# Auto-G16 v2.7 direct durable submission journal

Status: additive offline implementation candidate; production integration and
live operation remain blocked.

Task class: feature development / L3 transport and scheduler safety boundary.

## Sole ownership and non-authority

`direct_durable_submission_journal` is the sole repository-owned durable state
owner for the `direct_ssh_pbs` successor path. It owns only a local append-only
journal, an atomic cross-process consumption point, and a read-only restart
projection. It does not own or copy the existing direct profile, stable/fresh
root identity, descriptor capability, resource replay, live-approval replay,
transport, immutable upload, scheduler, qsub, qdel, deletion, or cleanup
owners. Its compatibility entry imports only the exact offline direct binding
and records its closed identity. Its fixed server-session entry additionally
requires one no-argument owner activation before use. Activation either
captures an already-completed, self-registered canonical W3 or, when W3 is
absent, executes only the fixed sibling source through an owner-opened no-follow
descriptor. That execution bypasses normal import-name resolution and requires
the exact reviewed full-source SHA-256, inode/metadata identity, unchanged
`sys.meta_path` identities and, for source execution, the exact isolated
Builtin/Frozen/PathFinder set, completed W3 owner registration, capability type,
and normalized exact predecessor-descriptor bytecode SHA-256. These identities
remain in an owner-private closure. There is no registration function accepting
a module, type, path, token, or caller value. A preloaded fake W3 module and a
fake meta-path finder therefore reject activation before journal creation, even
when a fake points at the real source path and supplies a same-named function
compiled with that filename. The server-session entry validates the binding
before and after calling the captured descriptor, which proves that the
still-unconsumed W3 capability is registry-bound to the same exact direct
transaction. Only then may W2 create the journal. W2 neither consumes nor
reconstructs either object. A journal document or claim never grants an
external effect.

The caller supplies an absolute, already-existing local state directory. That
directory is opened component-by-component with no-follow semantics, must be
owned by the current user, and must not be group/world writable. It is local
coordination storage only: it is never a server root, is never included in a
portable document, and cannot choose or replace the backend-owned server root.

## Durable order and crash rule

The exact mutation order is:

1. replay the canonical `direct_ssh_pbs` binding and derive one journal id from
   its profile, stable evidence, receipt, authorization, workspace, input,
   resource, scientific-task, attempt, and idempotency hashes. For the fixed
   server-session path, first require the exact direct transaction and exact
   still-unconsumed W3 capability to pass their existing owners' currentness
   checks without consuming either;
2. atomically create the derived journal directory with no replacement;
3. fsync the directory entry, create/fsync the owner lock and immutable
   manifest, then append/fsync
   `000000-submission-uncertain.json` with outcome `started`;
4. only after those fsyncs return a non-serializable, process-local,
   non-authorizing claim;
5. that same live claim may create exactly one shared
   `000001-terminal.json` slot containing a `completed` or `unknown` event.

The directory creation is the cross-process submission-consumption point. If publication
fails or the process crashes anywhere after that point, the partial or started
journal remains consumed and is never deleted, repaired, resumed, overwritten,
or retried. A started journal without a terminal record reconciles to effective
outcome `unknown`. A later process can only call `reconcile_read_only`; another
`consume_for_effect_once` fails closed before any effect claim is returned.

Every claim is bound to its creator PID, a process epoch and an owner-private
registry entry for that exact object identity. The mutable registry, its lock,
process token and epoch live only inside one factory-created owner closure;
the module namespace retains operation functions, not the mapping or a record
instance. Canonical records, descriptor identities and access projections are
tuple-based immutable values. The record freezes the exact binding hash,
journal id, started-event hash, owner thread lock, descriptor numbers, and
directory/lock `fstat` plus descriptor-flag identities. Every terminal call
compares the live object and freshly observed descriptors with that record
immediately before the terminal slot is touched. Field mutation, a closed
descriptor, or a reused descriptor number invalidates the terminal claim with
zero terminal write; only read-only reconciliation remains. The owner clears
its registry and changes the process epoch in
`os.register_at_fork(after_in_child=...)`. Exact claims are non-copyable and
non-serializable; reconstructed or field-copied objects are absent from the
registry and fail closed.

This is an ownership and accidental/hostile API-mutation boundary inside the
repository's supported Python process, not a sandbox against arbitrary code
execution in that same interpreter. Python code deliberately permitted to
walk and rewrite function closure cells, replace interpreter primitives, or
load native code is outside this contract and requires process isolation. The
owner does not claim protection against that stronger attacker.

`completed` and `unknown` do not have separate filenames. Both compete for the
same descriptor-relative `000001-terminal.json` creation with `O_EXCL`; that
single file is the common terminal reservation and immutable terminal record.
Only one outcome can win even if hostile writers race. A failed reservation is
never overwritten, deleted or retried, and a partial terminal file is retained
as corruption for read-only fail-closed handling.

## Outcome and reconciliation contract

The append-only event chain contains exactly one of these shapes:

- `started`: durable `submission_uncertain`, effective outcome `unknown` until
  an exact live claim appends a terminal observation;
- `started -> completed`: the common terminal slot contains one completed
  observation;
- `started -> unknown`: the common terminal slot contains one explicit
  uncertain observation.

Reconciliation takes the expected journal id and exact direct binding. Any
profile, stable-evidence, receipt, authorization-scope, workspace, input,
resource, scientific-task, attempt, idempotency, or binding-hash drift is
rejected. Unknown files, missing files, noncanonical JSON, duplicate keys,
hash-chain damage, symlinks, ownership/mode drift, and conflicting terminal
records all fail closed. Reconciliation takes a shared owner lock and performs
no write, retry, outcome promotion, external query, or automatic action.

The public Schema is a structural projection. Draft 2020-12 constrains the
three legal outcome/event-count shapes and canonical attempt-id grammar, but
has no standard keyword for equality between two dynamic instance values. The
Python owner therefore remains authoritative for the started-event-to-terminal
hash-chain link and additionally checks canonical bytes, exact event order,
exact builtin types, module/source identity, and the current canonical
direct-binding class. Schema validity alone is never authority.

## Compatibility and integration interface

This change is additive. It does not migrate, backfill, rehash, or rewrite
execution profile/authorization `/1` or `/2`, legacy execution-batch artifacts,
`legacy_rtwin_pbs`, or any existing resource/live/root owner. The existing
`contracts/direct-execution` package mapping carries the new Schema; the
`direct-durable-submission-journal.json` supplement adds only the new owner
module and this reference without duplicating that directory mapping.

A future separately reviewed general direct effect owner may continue to use
the compatibility entry in this order:

1. obtain and replay the exact root/resource/live/transport authorities from
   their existing owners;
2. call `consume_for_effect_once(local_state_dir, exact_direct_binding)`;
3. require the returned exact `DurableEffectClaim` immediately before its
   first possible external effect, while independently retaining all existing
   authority checks;
4. call `record_outcome_once(..., outcome="completed"|"unknown",
   evidence_sha256=...)` exactly once;
5. after process loss, call only `reconcile_read_only` and never automatically
   retry or reconstruct a claim.

The fixed trusted server-local session instead uses the closed ordering needed
by W5:

1. obtain an exact still-unconsumed direct transaction and W3 replay capability
   from their production sole owners;
2. call
   `consume_for_server_session_replay_once(local_state_dir,
   exact_direct_transaction, exact_w3_capability)`; W2 asks W3 to prove exact
   registry binding/currentness without consuming either, then fsyncs
   `started` and returns the exact durable claim;
3. consume the same exact W3 capability, which replays its predecessor
   currentness only after `started` exists;
4. issue W4 from those exact objects. Any W3 or W4 failure after `started`
   records `unknown` or leaves a started-only journal that is reconciled as
   unknown; no second durable or W3 claim is issued.

Preloaded or replacement `sys.modules` entries, first-registration poisoning,
fake `sys.meta_path` resolution, W3 class or descriptor replacement, source
drift, same-object reload/re-execution, and foreign or cross-bound
capability/transaction pairs are rejected before the journal directory or
`started` file is created. The compatibility
`consume_for_effect_once` binding-only entry retains its existing semantics.

This W2 interface intentionally provides no callback, command, argv, runner,
SSH, server path, upload, qsub, qdel, deletion, cleanup, retry, or legacy
fallback. Production remains blocked until those separate owners are composed
without weakening their contracts and receive independent L3 plus explicit
live-smoke authorization.
