## Scope and authority

This PR enacts the repository-owner decision recorded in the accepted
[platform portability RFC](v2.6-platform-portability-rfc.md): legacy backends
remain permanently fixed to `/home/user100/SDL`, while a future new backend
may use a different root only through a backend-owned, reviewed and hash-bound
policy.

This is a repository policy contract, not a backend implementation or an
execution authorization. It changes no existing schema, validator, adapter,
runtime, command, fixture or historical artifact. It performs and authorizes
no SSH, RTwin, PBS, Gaussian, deployment, submission, retry, cancellation,
cleanup, deletion, push, merge or release.

## Normative root ownership

1. `legacy_rtwin_pbs` and every historical/in-flight legacy replay use exactly
   `/home/user100/SDL`. No migration, rehash, backfill or policy reinterpretation
   is permitted.
2. A new backend owns its root through one closed, versioned profile contract.
   The root is mandatory, absolute, non-empty and included in that profile's
   canonical projection and payload hash. The backend owner, repository owner
   and server-safety owner review the exact policy before it can be supported.
3. The root cannot be selected, replaced or relaxed by a command-line option,
   environment variable, machine-local runtime setting, caller-supplied
   dictionary or path, backend auto-detection, fallback, or an
   "advanced override". Unknown, missing or conflicting policy fails closed.
4. A capability report may expose only the policy/profile/evidence digests and
   classification required by its sanitization contract. It must not publish
   private target or path values.

Repository review of this policy does not approve any particular future root.
Each exact root still requires the profile and evidence review below.

## Stable root identity and exact approval

Only the backend's workspace-policy owner may issue
`StableRootIdentityEvidence`. It is a closed, immutable and hash-bound
projection of the reviewed owner policy and expected root identity. Its
canonical projection must bind at least:

- schema and stable-evidence version, backend kind and backend-owner identity;
- exact profile ID and profile payload SHA-256;
- the reviewed root policy and the exact declared allowed root;
- the expected canonical allowed-root and existing-component identity chain,
  plus path-normalization and containment semantics;
- owner-validated project/scratch component grammar and derivation rules;
- `fresh_project_required=true`, `no_overwrite=true`, `no_symlink=true` and
  `no_delete=true`;
- the stable-evidence payload SHA-256.

The stable projection must not contain observation time, expiry, nonce,
receipt ID or another per-operation value. Unchanged owner policy and component
identity therefore reproduce the same stable hash; a changed root, policy,
profile or expected component identity changes it.

The human authorization for an operation must bind the exact profile hash and
stable-root-identity-evidence hash, as well as the exact project, task,
attempt, input and resource closure owned by the existing authorization
contracts. It also binds the required fresh-observation operation version,
maximum receipt age and `single_consumption_required=true`. It does not and
cannot pre-bind a future fresh-receipt hash. Showing or approving a root string
alone is insufficient.

## Fresh observation and check-to-use closure

Immediately before the first remote mutation, the workspace-policy owner must
use stable no-follow observations to issue a closed
`FreshRootObservationReceipt`. The receipt must bind at least:

- schema and observation-operation version;
- the approved profile hash and stable-root-identity-evidence hash;
- the authorization scope hash, exact operation/task/attempt and a fresh
  nonce;
- `observed_at`, `expires_at`, maximum-age compliance and receipt payload
  SHA-256;
- the actually observed root and existing-component identity chain;
- the derived project/scratch identities, containment and fresh-target result;
- comparison with the approved stable evidence and a fail-closed
  classification.

Time, expiry and nonce exist only in this fresh receipt, not in the stable
projection. The receipt references and proves equality with the approved
stable evidence; its own hash is necessarily fresh and is validated at
mutation time rather than pre-bound by the human approval. The portable
receipt alone is non-authorizing and cannot carry filesystem authority.

Together with the receipt, the owner must issue a non-copyable, single-use
descriptor- or capability-bound value for the same verified component
identities. The mutation owner must validate the current authorization,
profile hash, stable-evidence hash and fresh receipt, then consume that exact
capability in the same atomic operation or through descriptor-relative
no-follow operations. It must create/claim the project and perform the first
mutation through those already verified descriptors or handles; it must not
reopen, re-resolve or substitute a path after the check. A fixed remote helper
may satisfy this only when one owner operation performs both validation and
mutation against the same retained handles and returns a bound receipt.

Missing, partial, expired, replayed or unknown receipt; a changed
profile/root/component identity; a symlink or reparse point; containment or
freshness drift; a replaced handle; an attempted path reopen; or capability
consumption failure must stop before reservation, claim, write, transfer or
any other remote effect. Failure permits no fallback, retry, overwrite,
cleanup or deletion. If the backend cannot prove this check-to-use closure, it
must reject the operation.

## Filesystem invariants

- Resolve the allowed root, project and scratch paths canonically. Reject
  relative paths, parent traversal, root escape and every symlink or
  reparse-point component, even if the final resolved path would be contained.
- Derive project and scratch paths from owner-validated components. Do not
  accept caller-composed absolute paths or shell fragments.
- Claim only a fresh project by no-clobber creation. Refuse a non-empty or
  pre-existing conflicting destination and never overwrite an existing job.
- Keep scratch inside the exact project under the approved root.
- Provide no server-data delete, truncate, recursive replacement or cleanup
  operation. Scheduler cancellation remains a separately approved exact-job
  action and never grants file deletion.

## Compatibility, implementation gate and rollback

The existing `auto-g16-execution-profile/1`,
`auto-g16-execution-profile/2`, authorization, protected-submit, protected
runtime/state and legacy execution contracts remain fixed to SDL. This policy
does not make a non-SDL profile structurally or semantically valid.

A future new backend must add, rather than modify or reinterpret, any profile,
root-evidence and authorization successors needed to satisfy this policy. It
must have owner validators, schema/semantic parity, adversarial offline tests
and independent L3 review before non-SDL support can be claimed. Until then,
every executable backend remains SDL-only.

Rollback is a reviewed revert of this policy PR. It requires no runtime,
server-data or historical-artifact migration and authorizes no destructive
rollback.
