# Auto-G16 v2.6 protected production factory consumer

## Decision and unique entrypoint

`protected_production_factory_consumer.consume_protected_production_factory_once()`
is the only production factory-port consumer in this slice. It accepts only
the exact in-process `SealedProtectedCoordinatorFactoryPort`, claims it once,
replays the exact owner-issued objects returned by the coordinator and emits
one `SealedProtectedProductionFactoryResult`.

The result is an offline owner seal, not an `_LegacyEffectPlan`, adapter
request, runner request or execution capability. Its JSON document is a
non-authorizing audit projection. Raw JSON, hashes, the thirteen legacy plan
fields and Schema validity cannot replace the exact in-process result.

## Exact inputs and claim order

Before the coordinator claim, the consumer replays the canonical coordinator
module, port class, source bytes and document. The coordinator then owns this
fixed single-use order:

1. consume the exact legacy-root capability;
2. consume the exact resource replay capability;
3. replay the exact live-approval capability;
4. replay the exact uncertain runtime receipt; and
5. claim the exact production-ingress factory port.

The consumer then verifies the real classes, owner documents, source bytes,
object bindings and currentness of:

- `ProtectedLegacyEffectPlanFactoryPort`;
- `SealedProtectedRuntimeStateReceipt`;
- `CompletedPreQsubLiveApprovalReplay`;
- `ClaimedResourceEffectTimeReplay`; and
- `ConsumedLegacyWorkspaceDescriptorLease`.

It binds all five to the coordinator's exact project, input, attempt,
scientific task, idempotency, ingress, reservation, approval, resource and
legacy-root identities before sealing the result.

## Frozen legacy boundary

The consumer binds the actual `legacy_rtwin_pbs` module, source bytes,
`_legacy_effect_plan_from_transaction`, `_LegacyEffectPlan`,
`_legacy_raw_effect_owner_from_plan` and `_LegacyRawEffectOwner` identities.
It does not modify or invoke them. The current factory still requires the
CLI-owned `_LegacyTransactionPlan`; manufacturing that plan elsewhere would
create a parallel owner and is forbidden.

Consequently, success creates no legacy transaction plan, effect plan or raw
effect owner. It makes no adapter, runner, write, transport, qsub or remote
read call and does not connect `_submit_new()` or PR4. The later PR4 wiring
must remain a separately reviewed change at the frozen legacy-owner boundary.

## Failure and recovery boundary

A missing, foreign, spliced or drifted port fails before coordinator claim and
consumes nothing. Once `claim_once()` starts, any predecessor claim failure is
terminal for that port. No capability is replayed, reopened or reconstructed.
The durable state remains `effect_started_outcome_uncertain`; only the
existing coordinator's typed read-only reconciliation path may continue.

There is never an automatic retry, second physical attempt or second qsub.
The consumer does not write the runtime journal, package-4 ledger,
`job.events.jsonl` or `job.json`; those remain with their existing owners.
