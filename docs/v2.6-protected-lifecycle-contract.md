## Owner and phase map

`ProtectedLifecycleEvidence` contains exactly one field: exact typed PR4F
`ProtectedInvocationEvidence`. The PR4K loader no-follow stable-reads the fixed
adjacent `protected_invocation_contract.py`, compiles only those captured
bytes, verifies file/spec origin, and restores the previous `sys.modules`
entry after success or failure. A cross-load PR4F value is accepted only when
its class module, name, qualified name, dataclass field set, snapshot return
type, and snapshot code origin all identify that exact adjacent owner. A
mapping, same-shaped dataclass, sealed predecessor, caller path, stage list,
bytes, runner, command, backend, adapter, callback, or clock is rejected.

Production creates its owner with the module's fresh UTC clock on every seal
and every `assert_current()` replay. The fixed clock exists only behind the
private test token and is retained in the sealed test object so production
cannot inherit it. Before the lifecycle seal is issued, PR4F is sealed and
`assert_current()` completes owner, authority, local-state, ledger and stage
replay; the PR4F owner file identity is stable-read again afterward.

The existing owners establish three different orders that are not collapsed:

1. PR4D abstract protected submit: reserve once, stage exact bundle, submit
   once. Its reserve result atomically enters `submission_uncertain`.
2. PR4F future transaction: reserve attempt once, materialize exact bytes,
   transfer exact bytes, submit once.
3. Legacy transaction: prepare and stage before reservation, reserve, publish
   post-reservation local state, run the five pre-qsub effects, replay resource
   and live-approval evidence, mark qsub invocation started, run qsub once,
   classify, publish receipt, and reconcile state.

PR4K mechanically derives a **required future implementation order** from
those facts. It does not claim that order ran. In particular, the legacy
pre-reservation staging, caller CLI paths/commands, job-state publication,
raw-owner registry, and reconciliation implementation are not reusable
protected strategies.

## Portable and in-process boundaries

The portable document retains:

- the complete structurally validated PR4F document and its schema, ID and
  payload identity;
- exact duplicate identity, local-state, ledger, resources, transport and
  full ordered stage projections, so splices fail owner validation;
- the frozen PR4D, PR4F and PR4J orders;
- the required future implementation order and effect-time revalidation list;
- closed scope and status objects with `reserved=false`,
  `effects_performed=false`, `local_materialization_implemented=false`,
  `state_publication_implemented=false`, `actual_adapter_verified=false`,
  `reconciliation_implemented=false`, `runtime_config_read=false`,
  `raw_effect_owner_created=false`, and `automatic_retry=false`;
- the legacy compatibility/recovery gate and its own ID and payload hash.

Only the unconstructible in-process seal retains the typed PR4F evidence,
owner-issued PR4F bundle, source identities, local path/ledger identities,
stage source identities and private snapshots. It exposes only `document()`,
`assert_owner_sealed()`, and `assert_current()`. It has no reserve,
materialize, invoke, submit, status, fetch, cancel, cleanup, delete, runner, or
effect method and writes no file.

The closed Draft 2020-12 Schema references the separately frozen PR4F Schema
through `urn:auto-g16:protected-invocation-bundle:1`. Structural acceptance is
tested in both directions. Cross-field equality, IDs and digests remain owner
checks because standard Draft 2020-12 has no dynamic equality or hashing
keyword; Schema-valid identity/local/stage splices are still rejected by the
owner before a seal can exist.

## Compatibility and recovery gates

All historical schemas, fixtures and owners remain byte-for-byte frozen.
There is no migration, rehash, backfill, automatic promotion, adapter change,
or `LegacyTransportAdapter.invoke_reserved_once` change.
The additive
`tests/fixtures/rtwin_pbs/protected_lifecycle_contract.json` binds the exact
baseline commit/tree/parent and the final PR4K source, Schema, documentation
and test hashes without changing a predecessor fixture.

A future adapter may resume only after an independent task proves all of:

1. exact PR4K replay immediately before the first state change and again at
   every named effect-time boundary;
2. atomic PR4D reservation and `submission_uncertain` result consumption;
3. no-clobber materialization of every PR4F byte plus owner-sealed local state;
4. a protected factory that does not accept caller paths, mappings, commands,
   runners, callbacks, backends, clocks, or runtime overrides;
5. exact outcome, receipt and one-time reconciliation behavior;
6. the PR4J raw-owner registries are removed from any long process or the
   adapter proves their process lifetime and retained object count are bounded.

Offline validation grants no live, deployment, push, PR, merge, release, or
Skill synchronization authority.
