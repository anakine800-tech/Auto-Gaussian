## Honest validation layers

Standard Draft 2020-12 cannot express content hashing, derived IDs, equality
between duplicated projections, Python class identity, exact file origin, or
owner replay of actual artifacts. PR4K therefore does not claim complete
Schema/semantic-owner parity.

The public
`auto-g16-protected-lifecycle-structural-projection/1` document has fixed
machine-readable markers:

```json
{
  "structural_validation_only": true,
  "owner_replay_required": true,
  "schema_validity_grants_owner_acceptance": false,
  "schema_validity_grants_seal": false
}
```

The Draft Schema and
`validate_protected_lifecycle_structure()` have bidirectional
**acceptance-set parity for the constraints expressible by Draft 2020-12**.
This is not normalization-byte parity. For example, Draft accepts an integral
JSON number such as `3.0` for an integer field; the public structural
validator also accepts it and normalizes only its own returned Python value to
`3`. That normalization is not performed by, or evidence from, the semantic
owner. Every fixed field in `validation`, `scope`, `status`, and
`legacy_compatibility` requires an exact JSON/Python boolean. Numeric `0` and
`1` are rejected for every such field even though ordinary Python equality
would equate them with `false` and `true`.

Schema validity never means owner-accepted, verified, replayed, or sealed.
Only `ProtectedLifecycleContractOwner.seal()` can create the unconstructible
in-process capability, and that method accepts typed PR4F evidence rather than
a document. The private semantic check binds the structural projection,
lifecycle ID, and projection hash to an actual owner-issued, currently
replayed PR4F bundle.

The portable projection stores each PR4F summary once:

- PR4F schema, invocation ID, and invocation payload hash;
- ledger identity hash;
- stage manifest hash and artifact count;
- fixed PR4D, PR4F, PR4J, future implementation, and effect-time orders;
- closed scope, status, compatibility, and validation-layer markers.

The earlier duplicate `predecessor`, complete `protected_invocation`, and
`closure` fields were removed. Their equality and hash relationships could
not be expressed by standard Draft, so keeping them would make a structurally
valid splice look stronger than it is.

## Exact PR4F type and owner handoff

`ProtectedLifecycleEvidence` contains one field: PR4F
`ProtectedInvocationEvidence`.

At seal time PR4K stable-reads the adjacent
`protected_invocation_contract.py` with no-follow checks and binds the real
module object that already owns the evidence. Acceptance requires exact class
identity:

```text
type(evidence) is adjacent_module.ProtectedInvocationEvidence
```

There is no fallback based on `__module__`, class name, qualified name,
dataclass fields, snapshot method, or `co_filename`, and no reconstruction of
a caller lookalike into the expected class. The same module's PR4F owner must
then issue and replay the sealed PR4F bundle. Foreign identical modules,
ordinary cache replacement, forged filenames, and same-shaped classes fail
closed.

This boundary prevents accidental call-graph splices and pseudo-types. Python
underscores, tokens, and module metadata are not described as isolation from
arbitrary hostile code already executing in the same interpreter.

## Owner snapshot and current replay

After exact class-identity proof and before semantic validation or storage,
the lifecycle owner recursively rebuilds the complete typed PR4F evidence
twice. It accepts only the exact adjacent PR4F, PR4D, and PR4G evidence
dataclasses, exact builtin `dict` and `list` containers, exact `pathlib`
paths, and immutable builtin leaves. Caller-defined `Mapping`, container,
copy, deep-copy, and reduce behavior is neither trusted nor invoked. The two
owner-owned graphs must compare equal. A change between or during snapshots
fails closed.

Only the owner-owned evidence snapshot is passed to PR4F and retained by the
lifecycle seal. The caller's original mappings are never stored. Therefore:

- caller nested mutation after seal cannot change `document()` or invalidate
  `assert_current()`;
- concurrent caller mutation during `assert_current()` cannot affect replay;
- caller mutation during seal either fails closed or yields an owner snapshot
  that passes complete PR4F replay;
- real ledger, source, owner-file, or stage-artifact drift still fails closed.

The sealed capability rejects shallow copy, deep copy, and serialization. It
exposes only `document()`, `assert_owner_sealed()`, and `assert_current()`.

## Required future lifecycle

PR4K records but does not execute the following recovery order:

1. replay and assert the exact PR4F owner;
2. atomically reserve PR4D once and enter `submission_uncertain`;
3. materialize exact stage bytes with no clobber;
4. publish materialized local state;
5. run the fixed pre-submit effects once;
6. replay effect-time facts and live approval immediately before qsub;
7. publish qsub invocation started, run qsub once, and classify the outcome;
8. publish one immutable receipt if unique;
9. reconcile the exact attempt once.

All effect and implementation status fields remain false. The order is only a
future resume gate. It introduces no reserve, materialize, adapter, mutation,
status, fetch, cancellation, cleanup, delete, runner, command, backend,
callback, or runtime configuration API.

The PR4J long-process registry gate remains: a future long-running adapter is
blocked until strong-reference retention is removed or a bounded process and
object lifetime is proved.

## Compatibility and validation

PR4D, PR4G, PR4F, PR4I, PR4J, their schemas/fixtures, and
`legacy_rtwin_pbs.py` remain byte-for-byte frozen. There is no migration,
rehash, backfill, automatic promotion, adapter change, or
`LegacyTransportAdapter.invoke_reserved_once` change.

Tests cover:

- real pinned Draft 2020-12 acceptance-set parity for expressible structural
  constraints, including a generated `0`/`1` rejection matrix across every
  fixed validation/scope/status/legacy boolean, unknown fields, fixed orders,
  public-structural integral-float normalization, nonfinite values, malformed
  IDs and hashes;
- structurally valid identity, local/ledger, stage, and self-rehashed splices
  that remain explicitly non-owner-accepted and cannot issue a seal;
- forged filename/class/module/name/field/snapshot lookalikes, foreign
  identical modules, cache replacement, and legitimate exact PR4F evidence;
- caller mutation before, during, and after seal; hostile Mapping/dict/list
  subclasses whose copy/deep-copy/reduce hooks must not run; deterministic
  between-snapshot and single-nested-snapshot barriers; and concurrent
  `assert_current()`;
- real artifact drift, no-effect AST checks, frozen predecessor bytes,
  relocation, `.git`-free archives, import order, and the actual 78-file named
  Skill package layout.

Offline validation grants no live, deployment, push, PR, merge, release, or
Skill synchronization authority.
