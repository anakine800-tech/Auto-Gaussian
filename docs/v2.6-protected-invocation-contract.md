# Auto-G16 v2.6 owner-sealed protected invocation successor

Status: additive offline contract candidate for independent L3 review. It is
not an adapter, effect, reservation, execution approval, live validation,
deployment, migration, merge, or release record.

## Frozen scope and non-goals

This change adds `auto-g16-protected-invocation-bundle/1`, its owner, one typed
facade seal entry, and a mechanically extracted read-only legacy stage-byte
planner. It does not extend or reinterpret protected-submit `/1`, local-state
binding `/1`, execution request or authorization `/1` or `/2`, any
execution-batch version, historical CLI inputs, or stored artifacts.

No predecessor is migrated, rehashed, backfilled, or automatically promoted.
The successor has no method or scope for adapter invocation, reservation,
stage materialization, submit, status, fetch, cancel, cleanup, deletion,
retry, command execution, configuration access, or external action.

## ADR: mechanical legacy stage extraction

Decision: extract only selection and deterministic byte planning from
`legacy_rtwin_pbs.py`; do not create a second implementation.

The historical order remains:

1. approved Gaussian input basename and bytes;
2. same-stem `.json` when present;
3. same-stem `.xyz` when present;
4. explicit `%oldchk` when declared and owner-validated;
5. the fixed owner-rendered `<project>.pbs`;
6. `checksums.sha256` over items 1–5 in that order.

The legacy `stage()` still owns copy/no-overwrite behavior and now consumes
the same planner output for PBS and checksum bytes. Golden PBS, CLI, mocked
transaction, exception-category, and stage-field regressions must remain
unchanged. The source-file byte hash necessarily changes for this allowed
mechanical extraction; historical contract/Schema/PR4D/PR4G hashes stay
frozen, and the old legacy source hash remains recorded as predecessor
evidence rather than being silently rewritten.

## ADR: portable versus in-process state

The portable successor stores only:

- project, attempt, scientific task, input, idempotency and scientific
  identity hashes;
- PR4D and PR4G payload hashes;
- the unique relative local directory and fixed ledger basename;
- ledger artifact hash/size, revisions, self-hash projections and a
  domain-separated file-identity hash;
- exact resources and transport digests;
- ordered relative stage names, roles, hashes, sizes and aggregate manifest
  hash;
- fixed replay/future transaction order, explicit no-effect scope/policy, and
  its own payload hash.

It stores no absolute path, raw bytes, free basename, runtime configuration,
command, argv, shell, callback, executable, backend, adapter, credential, or
executable object.

Only the unconstructible in-process capability retains canonical local Paths,
initial file identities, stable source bytes, generated bytes, and the
existing owner-issued PR4D/PR4G objects. Its read-only replay also rechecks
that the predecessor authority window is current before replaying filesystem
identities. It has no effect method and acquires no ledger lock or reservation.

## Compatibility, migration and rollback

Compatibility is additive. Old requests, authorizations, bundles, bindings,
ledgers, CLI calls and directories continue under their historical owners.
There is no migration, rehash or backfill path into `/1`.

Before integration, rollback is deletion of only the new successor files and
the mechanical planner extraction while leaving all predecessors unchanged.
After any future artifact exists, `/1` must remain frozen; corrections require
a new successor version rather than reinterpretation.

## Residual gates

Offline evidence can support independent L3 review only. A future adapter task
must separately prove immediate replay, exact reservation transaction, byte
materialization, transport handoff, failure retention and one-time submit.
No result here authorizes adapter code, actual stage/submit/status/fetch/
cancel, SSH, PBS, Gaussian, deployment, Skill synchronization, push, PR,
merge, release, or live smoke.
