# Auto-G16 v2.6 execution-batch /3 reservation capability predecessor

## Decision and boundary

This additive offline predecessor extends only the existing package-4
execution-batch/resource owner. The owner validates and mutates the real
`gaussian-execution-batch/3` ledger under the existing sibling ledger lock,
durably records one `submission_uncertain` attempt, and issues one
`ExecutionBatchReservationCapability` before releasing that lock.

The capability is non-authorizing. It has no runner, transport, SSH, PBS,
Gaussian, qsub, retry, cancellation, cleanup, deletion, deployment, or live
operation surface. The legacy adapter, facade, transaction/effect-plan
factories, raw effect owner, protected owner-consumer/runtime-state/production
ingress owners, historical ledgers, Schemas, fixtures, and their bytes remain
unchanged.

## Exact lock and identity closure

The existing resource owner derives and validates every capability field inside
`execution_batch._locked(path)`:

| Binding | Locked owner source |
| --- | --- |
| scientific task | exact reviewed `/3` task and five-field scientific identity |
| attempt | deterministic batch ID plus exact idempotency key |
| project and input | fixed project policy plus reviewed input SHA-256 |
| resource gate | exact policy, gate, scheduler artifact, tier, cores, memory, walltime, and estimate |
| resource revision | the post-reservation `/3` ledger and resource-state revisions and hash |
| durable state | fsync-backed atomic ledger write completed with `submission_uncertain` |

The raw idempotency key remains only in the owner-private claim snapshot. The
portable projection contains its SHA-256 solely as descriptive binding. The
projection, its payload hash, a copied reservation mapping, or Schema validity
is never a capability.

## Registry, consumption, and permanent no-second-attempt rule

The exact capability object is held in an owner-private registry with one
private lock and the terminal states `unclaimed`, `claiming`, `claimed`, or
`failed`. Direct construction, subclass use, registry absence, copy, deepcopy,
pickle, sequential replay, and concurrent replay fail closed. One successful
claim returns one non-copyable exact-scope object and performs no external
effect.

Capability issuance also appends a hash-chained
`reservation_capability_issued` event to the same durable `/3` transaction.
Every later package-4 reservation checks that marker under the same ledger
lock. Once present for the task, a second physical attempt is permanently
refused even if another caller later proposes a different idempotency key.
Because qsub is outside this predecessor and a future qsub consumer must
require the one consumed capability, no second qsub is authorized.

If ledger publication succeeds but in-process capability construction fails,
the uncertain attempt and permanent marker remain durable. There is no
rollback, automatic reconciliation, retry, second reservation, or cleanup.
Recovery is limited to a separately reviewed read-only reconciliation path.
