# Auto-G16 Core/Approval guarded lifetime repair

FROZEN after independent source/contract review on 2026-10-12. Same authorized runtime task; narrows and corrects frozen runtime sections 1/1A's ambiguous "always release" wording. Applies only to handles opened by existing-only mutable entries. Creating constructors, legacy unguarded transactions, ordinary read_snapshot and persisted schema/record algorithms stay unchanged. No effect or approval authority.

Current source findings at bd2aa0e: Core _transaction places BEGIN outside its exception region and catches only Exception; caller-caught KeyboardInterrupt can leak an owned transaction. Core _db reads in_transaction before its PID guard. Core context finally can call SQLite.close in a child. Approval context finally releases pinned descriptors even when SQLite closure raised, and may retry close from a failed startup. Neither reports unknown closure with a retained process-local unresolved guard.

## Required repair

1. Guard process check occurs before ANY SQLite method/property at ordinary _db, transaction cleanup, explicit close and context exit. In a child, retain the inherited store+connection+guard pins in owner-private strong quarantine and reject; do not rollback/close/property-read. Tests must exercise actual context unwind while a parent transaction is active and then parent commit/lock integrity. Child process exit/exec is caller-controlled; this code never terminates it.
2. A SQLite close exception means unknown closure. Keep strong references to connection/store and guard, preserve all held target/ancestor FDs, poison handle, block same PID/dev/inode from a new guarded opener before opening any DB FD/SQLite. No reset or second close attempt; explicit close after quarantine rejects without SQLite access. On confirmed close set _closed and never close again. Context owns final pin release after every SQLite handle it owns is confirmed closed. Startup reader and writer share the guard; reader close success must not release lifetime pins before writer open.
3. Preserve original body/BEGIN/COMMIT exceptions if rollback, close, descriptor close or exit validation also fails; append static sanitized exception-class notes. Unknown rollback cannot be followed by resumed native work: poison and retain unresolved connection/pins if cleanup cannot be proved. No broad exception masking or original KeyboardInterrupt replacement. Partial construction and reader close failure use the same rules.
4. For guarded Core and Approval transactions only, verify idle/no existing transaction, record ownership immediately before BEGIN, and cover BEGIN/body/precommit/COMMIT/postcheck in one BaseException handler. On failure rollback only an owned still-active transaction and only in the original process. If COMMIT already succeeded, retain the native row and report error; no fabricated rollback or replay. A rejected pre-existing transaction is not consumed by that method (outer context may eventually rollback a lingering transaction on exit, as documented). Successful native record encoders and idempotence remain unchanged.
5. Permanently poison on identity/safety validation failures. Do not reacquire the database inode through another descriptor during its live SQLite locking interval. No new foreign-owner import or cross-owner persistence dependency. Quarantine lives separately inside each existing native owner, is not an approval store/schema/registry, and cannot generate a recovery authorization.
6. After SQLite is certainly closed, clear local FD ownership before one close attempt per FD, attempt every remaining FD even if one close fails, and preserve original error. Never retry a numeric FD. Ordinary complete close releases all pins; unknown SQLite closure is the explicit retained-resources exception.
