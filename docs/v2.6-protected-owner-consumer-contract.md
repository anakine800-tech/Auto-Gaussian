# Auto-G16 v2.6 protected owner consumer contract

## Decision and boundary

`auto-g16-protected-owner-consumer-contract/1` is the additive local
successor after the protected runtime/state contract. It is the sole owner
that consumes one exact current runtime/state capability and materializes the
local byte set needed by a future legacy effect-plan adapter. It performs no
transport, remote read, PBS, Gaussian, retry, cancellation, cleanup, deletion,
deployment, or live validation.

The owner issues only `ProtectedLegacyEffectPlanInputs`. It does not construct
`_LegacyTransactionPlan`, `_LegacyEffectPlan`, `_LegacyRawEffectOwner`, an
effect lifecycle, or a registry entry. The existing adapter and every actual
effect owner remain closed.

## Exact gap and ownership matrix

| Surface | Existing owner | Exact observed semantics | Successor ownership |
| --- | --- | --- | --- |
| Protected reservation | PR4L replays PR4D and stores its exact `consumption_sha256`, time, attempt and `submission_uncertain` state | This is not the legacy execution-batch ledger reservation | Reuse only as the protected authority; record that the legacy reservation is absent and is not an authority |
| Frozen local directory | PR4L | Exact topology is ledger + PR4F stage artifacts + PR4L state; extra files or replacement bytes invalidate `assert_current()` | Never modify it; copy only the sealed non-checksum stage bytes into an additive sibling directory |
| Runtime consumption and journal | runtime/state owner | Separate append-only ready → effect-not-started → uncertain receipts | Call its exact methods once; do not equate its journal with either reservation ledger |
| Legacy post-reservation files | legacy transaction | Adds `submission-intent.json`, excludes the local approval-consumption record from upload, rewrites `checksums.sha256`, then derives finite timeouts | Define a successor intent bound to the protected authority; reproduce the same upload/checksum ordering in the sibling bundle |
| Legacy effect-plan input | legacy module | Exact project, two directories, ordered paths/digests, finite timeouts, attempt/input identity and fixed runtime references | Bind the exact legacy module/class/constants/functions and issue the matching local input data only |
| First effect ordering | future adapter/effect owner | Must not begin before durable uncertainty | Fully fsync and replay the sibling bundle, persist effect-not-started, replay current identity/bytes, then persist uncertainty before issuing plan inputs |
| Reconciliation | future read-only observer plus runtime/state acceptance owner | Requires project, attempt, input, intent, receipt and exact scheduler evidence | Publish only the fixed local inputs and `observation_acquired=false`; perform no remote read or terminal acceptance |

All required authorities, fields, bytes and the local call chain are exact at
this boundary. No predecessor byte is modified, migrated, rehashed or
backfilled.

## Upload byte set and checksum semantics

The owner derives:

```text
<PR4L-local-dir-parent>/.auto-g16-protected-owner-consumer-v1/<attempt-id>/
```

Its exact upload order is:

1. every PR4F stage artifact except the predecessor
   `checksums.sha256`, preserving stage order and bytes;
2. canonical UTF-8 successor `submission-intent.json` plus one LF;
3. successor `checksums.sha256`.

The checksum file contains one line for every preceding upload artifact in
that order:

```text
<lowercase-sha256><two spaces><basename><LF>
```

It has no self-entry. PR4L's ledger, state record and predecessor checksum,
the protected live-approval consumption record, and runtime journal receipts
are not uploaded.

The intent records `auto-g16-protected-submit-reservation/1`, the exact
protected bundle/consumption identity, and two explicit false facts:
`legacy_execution_batch_reservation_present=false` and
`legacy_ledger_is_authority=false`. It therefore cannot be mistaken for the
old legacy reservation even though it retains the project/job/input/attempt
fields required by later read-only classification.

## Consumption, recovery and reconciliation

Normal ordering is:

1. exact module/class/source and runtime capability replay;
2. no-clobber sibling materialization and fsync;
3. final runtime and byte replay;
4. durable `effect_not_started` consumption;
5. another exact owner/source/runtime/byte replay;
6. durable `effect_started_outcome_uncertain`;
7. issue one non-copyable, single-claim plan-input capability.

A complete sibling bundle left before runtime consumption, or one paired with
an exact durable `effect_not_started` receipt, may be recovered without a
second consumption. Partial or mismatched bytes fail closed and are retained;
the owner never deletes or overwrites them. An already uncertain state cannot
issue another plan-input capability. It can expose only the fixed local
read-only reconciliation inputs, with no observation acquisition or effect.

## Validation layers and remaining gate

The Draft 2020-12 Schemas prove structural acceptance only. Public validators
also verify hashes and cross-field semantics. Only the exact canonical owner
replays predecessor capabilities, source/module/class identity, runtime
values, file identities and the receipt chain, then issues the in-process
seal. Schema validity never issues a seal.

A future separately reviewed effect-time slice must teach the exact legacy
module to consume this capability, construct one effect plan and bind the raw
owner/lifecycle without restoring caller path, configuration, command or
reservation authority. It must also acquire and accept real read-only
reconciliation evidence. This contract does neither.
