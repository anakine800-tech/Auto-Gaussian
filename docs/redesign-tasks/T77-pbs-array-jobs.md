# T77：PBS 队列中出现数组作业时，不再阻断核数统计、提交和监控

## 分支与目标

- 分支：`codex/t77-pbs-array-jobs`；基于最新 main，一张任务单一个 PR。**开发机做。**
- **开工条件：** T74 合并后开工（同时最多三条开发线）。本单优先于 T76。
- **来源：** T74 开发中确认，`status.parse_jobs` 遇到**其他用户**的数组作业号（`1234[5]`、`1234[5].example`）时报 `Invalid exact PBS job ID`。报错发生在按用户过滤之前，所以只要组里集群上有任何人提交了数组作业，`ag submit`（提交前核数统计）、`ag doctor`、`ag monitor` 都会失败。
- **目标：** 解析 `qstat -f` 时接受数组作业记录并做标记。其他用户的数组作业照常被过滤掉；本人的数组作业核数无法可靠统计，**明确拒绝**并说明原因。发给调度器的命令参数仍然只接受普通作业号。
- **属于硬内核（影响提交前的核数统计）：** 必须审阅，并在合并前完成真实验证。

## 允许改动的路径

- `ag/src/ag/status.py`：`parse_jobs`、`occupied`（以及 `core_breakdown` 中必要的配合）。
- `ag/src/ag/pbs.py`：`parse_nodes` 中节点 `jobs` 字段的作业号识别（原 T74 第 2 项）。
- `ag/src/ag/monitor.py`：只在显示本人作业列表时需要处理数组标记的地方改。
- `ag/tests/test_caps.py`、`ag/tests/test_queue.py`、`ag/tests/test_core.py`（覆盖 `parse_jobs`、`occupied` 的现有文件）、 `ag/tests/test_pbs.py`、`ag/tests/test_monitor.py`：新增用例（新建 `ag/tests/test_pbs_arrays.py` 也可以）。
- `README.md`：已知限制里 PBS 数组作业号那一条（第 262 行附近）；`docs/handoff-v4.md` 已知问题中对应一句。
- `docs/redesign-tasks/T77-pbs-array-jobs.md`：本任务单。
- **不改 `remote.job_id`、`remote.py`、`submit.py`、`fetch.py`、Slurm 相关代码。** 需要改就停下。

## 要做的

1. **先取真实格式（只读）：** 在开发机上对组里集群运行一次 `qstat -f`（只读），记录当时有没有数组作业，以及数组作业记录的实际样子（父作业 `1234[]` 还是子作业 `1234[5]`、有哪些字段，例如 `job_array_request`、`array_state_count`、`Resource_List.nodes`）。**脱敏后**（去掉主机名、用户名、队列名、路径）做成测试夹具。没有数组作业时写明“未观察到”，夹具按 Torque 文档格式构造，并在 PR 里注明。
2. **`parse_jobs`：** 作业号除普通格式外，接受 `数字[]` 和 `数字[数字]` 加可选 `.主机名`。数组记录加标记 `array: true`，其余字段照常读取。其他无法识别的作业号**仍然报错**（不能借机放宽成“认不出就跳过”）。
3. **`occupied`：**
   - 其他用户的记录（包括数组）照常跳过，与现在一致。
   - 本人的数组记录：报错，说明“本人有 PBS 数组作业，无法可靠统计已占用核数，拒绝提交；请在数组作业结束后再提交”。不估算、不按上限猜。
   - 本人的普通作业：统计方式完全不变。
4. **`pbs.parse_nodes`：** 节点 `jobs` 字段的作业号同样接受数组子作业格式，只用于统计节点已用核数。
5. **命令参数不变：** `remote.job_id`（用于 `qstat -f <作业>`、`qdel`）不改，仍拒绝数组作业号。逐一检查 `parse_jobs` 的所有调用处（`status.inventory`、`status` 单作业观察、`monitor`、`submit` 提交前复核、`fetch`），确认数组记录不会被当作某个 Attempt 的作业，也不会被拿去拼命令；在 PR 里逐处列出。
6. README 已知限制和 handoff 对应一句按实际结果更新。

## 不允许

- 不改本人普通作业的核数统计口径；不放宽 `max_committed_cores` 检查。
- 不跳过无法识别的作业号；不对本人数组作业估算核数。
- 不改 Slurm 路径。
- 夹具、日志、PR 中不出现主机名、用户名、队列名、路径。

## 测试

- 其他用户有数组父作业或子作业时：`parse_jobs` 成功，`occupied` 结果与没有这些记录时相同；`ag submit` 的核数统计、`ag doctor`、`ag monitor` 采样都正常。
- 本人有数组作业时：`occupied` 报上面的错误，`ag submit` 拒绝提交，且没有发出任何提交命令。
- 无法识别的作业号仍然报错。
- `remote.job_id` 仍拒绝数组作业号；单作业观察和取回路径行为不变。
- `parse_nodes`：节点 `jobs` 含数组子作业时，节点已用核数正确。
- 开发中只跑相关测试；推送前本地跑一次全量 `PYTHONPATH=ag/src python -m pytest ag/tests skills-next -q -rs`，之后以 CI 为准。敏感扫描与 `git diff --cached --check`。

## 真实环境验证（合并前，开发机）

- 用本分支在组里集群上运行只读的 `ag doctor`（看已占用核数）和一次 `ag monitor` 采样；与 main 版本的结果对比，本人普通作业的核数必须一致。
- 当时集群上有其他用户的数组作业：确认 main 版本失败、本分支成功。没有：写明“未观察到”，并说明只能以夹具为准。
- **负责人已同意（10-16）：用最小数组作业验证，验证后必须删除。** 步骤：
  1. Codex 先在开发机上准备好提交脚本并交给负责人核对：2 个子任务、每个 1 核、walltime 不超过 10 分钟、只运行 `sleep 300`，不读写任何研究文件，作业名用 `ag-t77-array-test`。
  2. 负责人在组里集群上手动提交，记下作业号。Codex 不提交、不删除任何作业。
  3. 作业还在排队或运行时，用本分支运行 `ag doctor`，确认给出“本人有数组作业”的拒绝信息；保存一份 `qstat -f` 输出，脱敏后与夹具核对格式。
  4. **验证一结束，负责人立即用 `qdel` 删除该数组作业**（Torque 下删除父作业号 `数字[]` 即删除全部子任务）。
  5. 负责人再运行一次 `qstat`，确认这个作业号已经不在队列里；然后用本分支再跑一次 `ag doctor`，确认恢复正常。
  6. PR 评论写明：已提交、已删除、删除后已核实不在队列中（不写作业号、主机名和用户名）。**没有写明已删除并核实，本 PR 不审阅通过。**
  - 删除失败或作业状态异常：停下，由负责人处理，不要再提交新的测试作业。
- 研究 A 只做观察，不作为验证对象。结果写进 PR 评论，不写主机、路径和用户名。
