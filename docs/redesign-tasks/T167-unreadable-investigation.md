## 要做的

1. 通过可访问的 Git 历史、PR diff、评论和现存文档重建 T62 第 1 项及 T65 回退的时间线。每项写实际提交、原始 URL/文件位置、属于开发报告/审阅/现场转达中的哪类证据；不存在的原始日志明确无法取得，不补造。
2. 对比 receipt、output_observation、incomplete_output_observation 在改前、T62、回退后和当前版本的具体判断：
   - 文件存在与可读；
   - 文件确实不存在；
   - 上级目录无法进入/权限不可判断；
   - 符号链接、非普通文件、竞态；
   - shell 工具退出码、stderr 文本及本地解析分支。
   只读取与这些路径有关的历史代码，旧规则不能成为当前执行指令。
3. 将“曾返回 unreadable”与“为何返回 unreadable”分开。对每个假设写可解释的代码路径、需要的前提、支持/反证、当前证据级别；不能从一个错误词猜权限故障。
4. 在临时目录搭建合成文件/目录布局，尽量复现普通存在、真正缺失、不可进入父目录、不可读文件、链接、文件替换等最小场景；不触碰真实路径。无需全新框架；可使用从实际实现取得的固定命令构造和本地假 transport。
5. 权限场景须核对实际有效权限和运行身份，若宿主权限使该场景无法真实成立，写“未能在本环境复现”，不能把手工伪造 stderr 当作 OS 权限复现。分别报告解析器合成测试与本地真实文件系统观察。
6. 对英文/非英文消息、工具版本差异、普通文件与父目录缺失的差异做适量核查，只覆盖有代码依据的假设；不为追求一个根因扩成全面远程平台重构。
7. 交付明确分层结论：
   - 原事故根因：已证实/可疑但未证实/证据不足；
   - 当前实现中可独立复现的缺陷：有则给触发、影响、最小修复范围；
   - 无法追溯的历史部分：准确缺什么；
   - 后续是否值得开实现单及其最小测试/现场验证要求。
8. 即使原根因无法确定，也可依据现有可复现缺陷提出有限修复建议；反过来，当前测试正常不证明原事故从未发生。没有可证实缺陷时不为凑任务而修改代码。
9. 后续若要改 remote/status/receipt 生产路径，另写实施单并在非研究验证对象上完成合并前真实验证；明确命令、范围、授权状态和停止条件。本单不创建/取消/提交作业，不恢复 T62 的“研究使用顺带验收”安排。
