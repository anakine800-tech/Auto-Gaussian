# Auto-G16 v2.6 deterministic local-state binding design

Status: additive offline contract proposal for a future protected successor.
It is not an execution approval, invocation contract, adapter, effect, live
test, migration, deployment, or release record.

## Scope and frozen predecessors

This change adds `auto-g16-local-state-binding/1` only. It does not change the
legacy CLI, historical local directories, execution request or authorization
`/1` or `/2`, `auto-g16-protected-submit-bundle/1`, any ledger version, or any
existing stage, submit, status, fetch, cancel, cleanup, replay, or reservation
behavior. No predecessor is migrated, rehashed, backfilled, or reinterpreted.

The fixed layout applies only to a future protected successor:

```text
<reviewed-workspace-root>/outputs/<project>/<attempt_id>/
<reviewed-workspace-root>/outputs/<project>/<attempt_id>/execution-batch-v3.json
```

`project` and `attempt_id` are never independent path inputs. The local-state
owner obtains them from a freshly owner-sealed PR4D protected-submit closure.

## ADR: local-directory occupancy policy

Decision: at seal and replay time, the derived local directory must already
exist, be owned by the current user, and contain exactly one entry:
`execution-batch-v3.json`.

This is intentionally stricter than the legacy stage path. Legacy stage may
create or update `job.json`, `job.events.jsonl`, submission intent or receipt
records, a staged Gaussian input, a PBS file, and checksum state. Accepting any
pre-existing protected or unrelated entry would make it impossible for this
contract-only change to distinguish a harmless file from partial staging,
recovery, replacement, or overwrite ambiguity. The first version therefore
fails closed for every additional entry, including lock and temporary files.
A later relaxation requires a separately reviewed versioned successor; it
must not change `/1`.

The local-state path owner creates no workspace or local-state directory,
changes no existing permission, acquires no legacy ledger reservation lock,
and writes neither the ledger nor the binding. The reused PR4D closure retains
its already-reviewed, process-private temporary validation behavior; this
successor neither broadens nor reclassifies that predecessor behavior.

## Portable contract and in-process seal

The JSON object stores no absolute path. It records:

- fixed layout version and relative local-directory and ledger paths;
- domain-separated digests of the canonical workspace root and local
  directory;
- exact ledger artifact hash, size, payload hash, revision, resource-state
  revision/hash, domain-separated batch-identity digest, and review hash;
- protected bundle hash plus project, attempt, scientific task, input, and
  idempotency-key hash;
- explicit no-effect, no-migration, no-write, no-lock and future-successor-only
  policy flags; and
- its own payload hash.

The in-process `LocalStatePaths` and `SealedLocalStateBinding` are owner-issued
only. They retain canonical `Path` values and initial directory/file
identities. Their read-only assertion path repeats the no-follow load,
owner-validates the current `/3` ledger, requires the original identities and
bytes, and rechecks the portable binding. They hold no command, callback,
configuration, backend, adapter, or effect.

## Future gate

PR4F must bind the exact `local_state_binding_payload_sha256` into its
successor contract. A later, separately reviewed adapter must reassert the
sealed local-state binding immediately before any effect and then use the
existing ledger owner under its own reservation transaction. This proposal and
all offline test evidence remain non-authorizing.
