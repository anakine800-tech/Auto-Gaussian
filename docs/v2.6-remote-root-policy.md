## Scope and authority

This PR enacts the repository-owner decision recorded in the accepted
[platform portability RFC](v2.6-platform-portability-rfc.md): legacy backends
remain permanently fixed to `/home/user100/SDL`, while a future new backend
may use a different root only through a backend-owned, reviewed and hash-bound
policy.

This is a repository policy contract, not a backend implementation or an
execution authorization. It changes no existing schema, validator, adapter,
runtime, command, fixture or historical artifact. It performs and authorizes
no SSH, RTwin, PBS, Gaussian, deployment, submission, retry, cancellation,
cleanup, deletion, push, merge or release.

## Normative root ownership

1. `legacy_rtwin_pbs` and every historical/in-flight legacy replay use exactly
   `/home/user100/SDL`. No migration, rehash, backfill or policy reinterpretation
   is permitted.
2. A new backend owns its root through one closed, versioned profile contract.
   The root is mandatory, absolute, non-empty and included in that profile's
   canonical projection and payload hash. The backend owner, repository owner
   and server-safety owner review the exact policy before it can be supported.
3. The root cannot be selected, replaced or relaxed by a command-line option,
   environment variable, machine-local runtime setting, caller-supplied
   dictionary or path, backend auto-detection, fallback, or an
   "advanced override". Unknown, missing or conflicting policy fails closed.
4. A capability report may expose only the policy/profile/evidence digests and
   classification required by its sanitization contract. It must not publish
   private target or path values.

Repository review of this policy does not approve any particular future root.
Each exact root still requires the profile and evidence review below.

## Canonical root evidence and exact approval

Only the backend's workspace-policy owner may issue canonical root evidence.
The evidence is closed, immutable and hash-bound. Its canonical projection
must bind at least:

- schema and evidence version, backend kind and backend-owner identity;
- exact profile ID and profile payload SHA-256;
- the reviewed root policy and the exact declared allowed root;
- the canonically resolved allowed root identity and path-normalization
  semantics;
- proof that the root and every existing component were examined without
  following symlinks or reparse points;
- the derived project and scratch identities plus their containment result;
- `fresh_project_required=true`, `no_overwrite=true`, `no_symlink=true` and
  `no_delete=true`;
- observation time, evidence validity window and the evidence payload SHA-256.

The human authorization for an operation must bind the exact profile hash and
canonical-root-evidence hash, as well as the exact project, task, attempt,
input and resource closure owned by the existing authorization contracts.
Showing or approving a root string alone is insufficient.

Immediately before the first remote mutation, the backend owner must reproduce
the canonical evidence from stable no-follow observations and compare the
profile and evidence hashes in constant time. Missing, partial, expired or
unknown evidence; a changed profile/root/component identity; a symlink or
reparse point; containment drift; or a non-fresh target invalidates the
approval and stops before mutation. It cannot trigger fallback, retry,
overwrite, cleanup or deletion.

## Filesystem invariants

- Resolve the allowed root, project and scratch paths canonically. Reject
  relative paths, parent traversal, root escape and every symlink or
  reparse-point component, even if the final resolved path would be contained.
- Derive project and scratch paths from owner-validated components. Do not
  accept caller-composed absolute paths or shell fragments.
- Claim only a fresh project by no-clobber creation. Refuse a non-empty or
  pre-existing conflicting destination and never overwrite an existing job.
- Keep scratch inside the exact project under the approved root.
- Provide no server-data delete, truncate, recursive replacement or cleanup
  operation. Scheduler cancellation remains a separately approved exact-job
  action and never grants file deletion.

## Compatibility, implementation gate and rollback

The existing `auto-g16-execution-profile/1`,
`auto-g16-execution-profile/2`, authorization, protected-submit, protected
runtime/state and legacy execution contracts remain fixed to SDL. This policy
does not make a non-SDL profile structurally or semantically valid.

A future new backend must add, rather than modify or reinterpret, any profile,
root-evidence and authorization successors needed to satisfy this policy. It
must have owner validators, schema/semantic parity, adversarial offline tests
and independent L3 review before non-SDL support can be claimed. Until then,
every executable backend remains SDL-only.

Rollback is a reviewed revert of this policy PR. It requires no runtime,
server-data or historical-artifact migration and authorizes no destructive
rollback.
