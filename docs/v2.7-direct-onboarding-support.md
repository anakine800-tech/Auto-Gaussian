## Scope and non-authority

This milestone adds an independent offline onboarding command, a field-level
migration guide, an exact support matrix, and a static redacted issue template.
It describes only the offline capabilities integrated by the three merged
milestones. It does not add or authorize SSH, PBS, Gaussian,
qsub, qdel, upload, fetch, inspection, cancellation, deletion, cleanup,
deployment, live smoke, or scientific acceptance.

The direct backend has exactly these statuses:

- `offline_synthetic`
- `production_blocked`
- `live_not_ready`

It is not `backend_supported`, production-ready, transport-authorized, or
live-ready. Schema validity and an onboarding template are not capabilities.

## Offline quickstart

Run these commands only with local synthetic or separately reviewed sanitized
documents. The direct command has no path argument and reads a profile only
from stdin.

Create a non-authorizing onboarding checklist:

```bash
./scripts/python core scripts/direct_onboarding.py init direct-profile-001
```

This emits an `auto-g16-direct-onboarding-template/1`. It is not an execution
profile, approval, stable root evidence, authorization, descriptor capability,
or production configuration. Human review must create the owner inputs and the
`direct_root_owner_contract` owner must build and validate any real candidate
profile `/3` outside this onboarding command.

Validate one exact direct profile `/3` without revealing it in argv:

```bash
./scripts/python core scripts/direct_onboarding.py validate < reviewed-direct-profile-v3.json
```

Create a redacted offline diagnosis:

```bash
./scripts/python core scripts/direct_onboarding.py doctor < reviewed-direct-profile-v3.json
```

For historical execution-profile `/1`, use its existing command instead of the
direct CLI:

```bash
./scripts/python core scripts/platform_contracts.py validate profile historical-profile-v1.json
```

Legacy `/2` artifacts remain with the existing transport-authority and legacy
owners described in
[`v2.6-transport-authority-closure-design.md`](v2.6-transport-authority-closure-design.md).
There is no direct onboarding migration command for `/2`.

Every direct command is offline-only. `init` accepts only a portable profile
ID. `validate` and `doctor` accept only stdin JSON. There is no `--root`, root
environment variable, root runtime setting, path selector, backend selector,
scheduler selector, command, argv, callback, arbitrary shell, or fallback.

## Field-level migration guide

### Facts

- `/1`, `/2`, and `/3` are different closed schemas with different owners and
  semantics. A shared field name or value is not migration authority.
- Historical `/1` and `/2` artifacts replay unchanged through their historical
  owners. Their bytes, hashes, root, and approvals are not rewritten.
- Every new direct execution requires a newly human-reviewed direct profile
  policy, stable evidence, execution-profile `/3`, and authorization `/3`.
- Root cannot come from a flag, environment variable, runtime setting, caller
  argument, legacy artifact, or onboarding template.

### Mapping and non-mapping

| Concept/field | `/1` | `/2` | `/3` direct treatment |
| --- | --- | --- | --- |
| `schema` | `auto-g16-execution-profile/1` | `auto-g16-execution-profile/2` | Must be newly issued as `auto-g16-execution-profile/3`; never auto-upgrade |
| `profile_id` | Historical portable ID | Historical legacy successor ID | Human may select a reviewed new ID; no automatic copy or identity equivalence |
| `backend_kind` | Historical enum included legacy and direct expressibility | Closed to `legacy_rtwin_pbs` | Closed to `direct_ssh_pbs`; no translation or fallback |
| Transport config | `transport_config_ref` plaintext private reference | `transport_config_bindings` for fixed legacy two-hop owner refs/hashes | No direct mapping; create a new reviewed `transport_identity_binding_sha256` for the direct topology |
| `transport_identity_binding_sha256` | Historical `/1` binding semantics | Legacy two-hop binding semantics | Same field spelling does not permit reuse; bind newly reviewed direct evidence |
| `scheduler_dialect` | `pbs_legacy_v1` | `pbs_legacy_v1` | Token remains fixed but must be replayed inside the new `/3` owner chain; it alone grants nothing |
| Gaussian runtime | Inline `gaussian_runtime` | Inline legacy `gaussian_runtime` | No field mapping; bind a separately reviewed `gaussian_runtime_binding_sha256` |
| Workspace/root | Inline fixed-SDL `workspace_policy` | Inline fixed-SDL `workspace_policy` | No mapping; a new profile policy owns mandatory `declared_allowed_root`, stable identity evidence, and hash bindings |
| Resource catalog | Inline `resource_catalog` | Inline legacy `resource_catalog` | No rehash/backfill; bind a newly reviewed `resource_catalog_sha256` |
| Capabilities | Historical platform capability vocabulary | Historical legacy capability vocabulary | Exact direct-root-only capability list; not backend/live support |
| `profile_payload_sha256` | Hash of exact `/1` bytes | Hash of exact `/2` bytes | Must never be reused or recomputed as migration; owner builds a new `/3` hash |
| `profile_policy` | Absent | Absent | New mandatory reference to reviewed direct profile-policy `/1` |
| `root_policy_owner_version` | Absent | Absent | New mandatory direct-root owner version |
| `stable_root_identity_evidence_sha256` | Absent | Absent | New mandatory stable evidence binding |

### Required human review

1. Confirm the intended backend is exactly `direct_ssh_pbs` and that only
   offline onboarding is currently requested.
2. Review transport identity, Gaussian runtime binding, resource catalog, and
   the backend-owned root policy through their exact owners.
3. Review stable root identity evidence and confirm that the root is mandatory,
   profile-owned, and hash-bound with no override surface.
4. Have `direct_root_owner_contract` build and validate a new profile `/3` and,
   separately, a new authorization `/3`. Neither is a production capability in
   the current offline-only release scope.
5. Keep historical artifacts unchanged and record every remaining production
   gap before any future live proposal.

### Blockers

Stop without migration if an input is unknown, unsupported, `/1`, `/2`, has a
foreign backend, lacks exact owner evidence, requests root override, proposes
automatic rehash/backfill, or treats a valid profile as capability. Direct
production and live use also remain blocked by every gap in the production gap
matrix.

## Static redacted issue template

This is a static checklist, not an automatic sanitizer. Manually review every
line before sharing it. A full profile or authorization hash can correlate
reports and private configuration; prefer an 8-12 character hash prefix and
share even that only after the user confirms the correlation risk is
acceptable.

```text
Auto-G16 version:
OS family only (for example: macOS, Windows, Linux):
Backend enum (legacy_rtwin_pbs or direct_ssh_pbs):
Command enum (init, validate, doctor):
Error code only:
Profile hash prefix (8-12 characters; optional; user-confirmed):
Authorization hash prefix (8-12 characters; optional; user-confirmed):
Offline doctor redacted summary (optional; manually reviewed):

Required confirmation before posting:
[ ] I did not paste a host, user name, IP address, SSH config, private path,
    server root, raw profile, raw authorization, raw scientific input, raw log,
    Gaussian output, checkpoint, job ID, private key, password, or token.
[ ] I did not paste a full profile/authorization hash without separately
    reviewing and accepting its correlation risk.
[ ] I understand this report does not authorize deployment or live work.
```

Do not attach raw files. Do not expand an error report into a connectivity
probe, retry, qsub, qdel, cleanup, deployment, or live smoke.

`scripts/platform_contracts.py`, historical schemas/artifacts, the legacy root
owner, legacy facade/factory/raw owner, or scientific logic. The
`auto-g16-rtwin-pbs` Skill name remains unchanged. The package supplement maps
only the direct onboarding script and this document; repository files are not
copied into the Skill tree and no deployment is performed.
