# Auto-G16 v2.6 protected job/runtime coordinator

## Boundary

`protected_job_runtime_coordinator` is the sole cross-owner transition caller.
It does not replace any existing authority:

- `protected_runtime_state_contract` remains the only runtime-journal writer;
- package-4 `resource_efficiency` remains the `/3` ledger owner;
- legacy `job.events.jsonl` and `job.json` are derived compatibility
  projections, never authority;
- live approval, resource replay and legacy-root capabilities remain owned by
  their integrated predecessor modules; and
- `legacy_rtwin_pbs` remains the sole future `_LegacyEffectPlan` and
  `_LegacyRawEffectOwner` owner.

The coordinator accepts exact in-process capabilities only. Raw JSON, hashes,
paths, CLI values, Schema acceptance and the old thirteen plan fields cannot
authorize any transition.

## State and durable order

The `/3` ledger is already durably `submission_uncertain`, and the existing
owner-consumer has already published the exact
`effect_started_outcome_uncertain` runtime receipt, before coordinator entry.
Port issuance validates all exact inputs and changes no persistent state. The
port's sole future
`claim_once()` then:

1. validates all exact module, class, source, object, bytes, identity and
   currentness bindings against that exact uncertain receipt;
2. consumes the exact legacy-root, resource-replay and live-approval
   capabilities once, completing their owner-private final replay;
3. claims the existing production-ingress plan-input port once; and
4. returns the exact owner-issued objects from the already sealed coordinator
   factory port.

The port is non-copyable, non-serializable and single-claim. Claiming it only
returns the exact owner-issued objects. It never calls the legacy factory,
creates an effect plan/raw owner, runs a command, performs transport, qsub,
remote reads, cleanup or any other external effect.

Any identity, bytes, state or currentness mismatch stops with no new
coordinator-driven persistent state. Any failed capability claim is terminal
and reconciliation-only; capability replay is never retried. Runtime journal
transitions remain exclusively in the existing runtime/owner-consumer and
typed reconciliation owners.

## Recovery and reconciliation

Restart never reconstructs an in-process effect capability. Recovery order is:

1. take the exact attempt lock for read-only recovery;
2. validate the `/3` ledger's permanent reservation and
   `submission_uncertain`;
3. replay the complete protected runtime journal;
4. reject effect recovery when any in-process capability is absent;
5. acquire typed read-only observation outside this contract;
6. accept only `submitted_unique` or `definitely_not_submitted`;
7. reconcile the `/3` ledger through its existing owner and lock;
8. append runtime `accepted_terminal` through the existing runtime owner; and
9. rebuild legacy job-state projections last.

Unknown, stale, conflicting or multiple-match evidence changes no state.
Every terminal path permanently forbids a second physical attempt, a second
qsub and automatic retry.
