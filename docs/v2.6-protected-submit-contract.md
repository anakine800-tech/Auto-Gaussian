# Auto-G16 v2.6 PR4D owner-sealed protected-submit contract

Status: additive offline contract support; no adapter implementation or actual
validation

Task class: feature development / L3 execution-authority boundary

## ADR: one first-version protected-submit bundle

Decision: add `auto-g16-protected-submit-bundle/1`, owned by
`protected_submit_contract.py`, with the public Schema file
`contracts/execution/protected-submit-bundle.schema.json`.

This is a new artifact family, so repository convention uses the un-suffixed
filename for `/1`; existing `-v2` filenames remain successors of historical
`/1` families. The artifact is placed in `contracts/execution` because it
binds the backend-neutral authority closure. The current
`auto-g16-rtwin-pbs` named package remains its initial owner package and maps
the single root owner into the packaged `scripts` directory.

Rejected alternatives:

- Changing execution request or authorization `/1` or `/2` would reinterpret a
  frozen identity handshake and is forbidden.
- Extending a live-approval Schema would couple one human approval generation
  to transport implementation details and would not close stage identity.
- Adding submit behavior to `transport_authority_closure.py` would weaken its
  deliberate read-only boundary.
- Letting the legacy transaction validate a caller mapping would make the
  adapter an authority owner and duplicate existing validators.

## Owner composition

The owner accepts raw evidence only at its seal boundary. It delegates to the
existing owners for:

1. exact input receipt reconstruction and live-approval replay;
2. execution-batch `/3`, scientific-task and resource-state replay;
3. resource policy, gate and scheduler-snapshot replay;
4. execution request/authorization `/1` and `/2`, profile, identity binding,
   Stage A/B receipts and the nested handshake receipt; and
5. locked trusted-current-time single-use consumption.

The portable bundle contains no source path or raw artifact bytes. It also
contains no command, argv, shell, backend selector, host, config reference,
callable or executable object. The only path-like value is the immutable
policy constant `/home/user100/SDL`; there is no root or work-directory
override.

The owner computes:

- the exact Gaussian input hash;
- one scientific-task identity digest;
- the deterministic attempt ID and the idempotency-key digest;
- the workspace-policy digest;
- the stage manifest and bundle hashes from exact input bytes plus an
  owner-derived typed scheduler binding in fixed role order, using
  length-delimited byte framing for the bundle hash;
- every predecessor artifact/file/payload binding;
- a protected authority ID and nonce derived from the exact live-approval
  artifact; and
- the final canonical bundle payload hash.

Callers cannot manufacture an owner-sealed object by validating JSON. Public
JSON validation remains useful for portable topology, but only complete
predecessor-owner replay issues the in-process seal.

## Structural Schema validity and owner validity

The public Draft 2020-12 Schema and the Python owner have deliberately layered
claims rather than a claimed complete acceptance-set equality:

- `jsonschema.Draft202012Validator` proves the closed object topology, JSON
  types, constants, patterns and array shape.
- Timestamp strings have one structural representation,
  `YYYY-MM-DDTHH:MM:SSZ`. The standard Schema regex can describe that canonical
  shape but cannot prove every Gregorian calendar date. The owner parses the
  value and rejects impossible dates while accepting real dates such as leap
  day.
- Draft 2020-12 treats a mathematically integral JSON number such as `1.0` as
  an integer and rejects booleans as integers. The owner matches that rule,
  then normalizes integral values to JSON integers before computing or checking
  the portable self-hash. Thus `1` and `1.0` have one canonical bundle byte
  representation rather than two authority identities.
- Schema validity never proves the self-hash, predecessor artifacts, trusted
  clock, single-use state or in-process seal. Those remain owner validity.

The standards-validator test environment is independently pinned by
`requirements/schema-validation.txt` and
`requirements/schema-validation.lock.txt`. It is test-only: it is not a core
runtime, chemistry runtime, adapter, transport or scientific-execution
dependency. Core compatibility and source-archive full-suite jobs retain no
third-party dependency; when the validator is absent the dedicated standards
test reports an explicit skip instead of claiming Draft validation.

The backend-neutral facade exposes only:

- `seal_protected_submit_bundle(*, evidence)` for non-consuming owner replay;
  and
- `reserve_protected_submit_bundle_once(*, evidence)` for the final
  trusted-time replay plus reservation.

Neither API accepts time, consumption state, effect behavior, an adapter or a
backend selector. Existing predecessor owners are loaded from their exact
repository or packaged origins while caller runtime-configuration variables
are isolated, so sealing does not consult machine-local transport settings.
The facade loads `protected_submit_contract.py` only from its own resolved
directory, verifies both file and import-spec origins, and restores only the
pre-existing same-name module-cache entry. Caller-path shadows, a preloaded
same-name module and another relocated root/package owner cannot become the
facade owner. Both public entry points necessarily pass through that exact
owner; plain Schema validation is not a sealing alternative.

## Gate before effect and failure state

Sealing is non-executable. Reservation repeats the complete closure under the
existing state owner's lock using the owner's timezone-aware UTC clock. Any
missing, unknown, mismatched, stale, expired, revoked, consumed or replayed
value stops before reservation. The owner performs no automatic completion,
migration or retry.

The fixed effect order is:

1. `reserve_once`;
2. `stage_exact_bundle`;
3. `submit_once`.

The reserved value starts in `submission_uncertain` before any future effect.
The state owner permits at most one successful reservation for an exact
authority, attempt, idempotency key, live approval and attestation nonce set.
PR4D deliberately provides no effect callback and calls no adapter. A future
adapter exception must retain that reservation and may proceed only through
the existing read-only reconciliation semantics; it must not retry, cancel,
clean up or delete.

## Authority boundary

The bundle authorizes exactly one future immutable stage plus one submit. It
does not authorize status, monitor, fetch, cancel, scheduler-zombie cleanup,
server-data cleanup, delete, command execution, backend choice, scientific
change or resource change. It does not prove that an adapter, RTwin, SSH, PBS,
Gaussian or remote environment works.

Input receipts `/1`–`/3`, resource-bound live approvals `/9`–`/11`, execution
batch `/3`, resource gate `/2` and the transport successor remain independent
predecessor owners. Historical artifacts are not migrated, rehashed or
backfilled.

## Validation claims and remaining gate

Code support in PR4D consists only of a closed Schema, owner composition,
owner-sealed typed values, a narrow public facade and placeholder-only offline
tests.

Offline evidence may prove bounded structural checks, standards-validator
behavior, owner semantic checks, exact binding failures, single-consumer
behavior, uncertain-state retention, legacy compatibility, packaging and
source relocation. It is not actual validation evidence.

After the candidate bytes are frozen, the branch still requires an independent
L3 review. A later adapter task requires its own contract consumption design,
review and separately approved actual validation. PR4D does not authorize
push, PR, merge, release, deployment, Skill synchronization or live smoke.
