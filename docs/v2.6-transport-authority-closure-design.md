The `/2` profile is restricted to `legacy_rtwin_pbs`, exact two-hop identity
topology and fixed `/home/user100/SDL`. It replaces the `/1` single private
`transport_config_ref` with a closed binding whose two logical references are
`rtwin_ssh_config` and `windows_server_config`. Only their adapter-derived

The `/2` request is the only new authority intent. The `/2` authorization must
reference that exact request ID and canonical payload digest; it cannot use a
request `/1` as new intent. The historical `/1` request and authorization remain
byte-frozen provenance only, and the owner verifies that the actual `/1`
authorization internally references the actual `/1` request before accepting
either overlay.

The `/2` authorization is an additive human-approved record, not an in-place
reinterpretation of PR3. Its first two operations must equal the PR3 `/1`
operations after adding the explicit `single_attempt=true` marker. The third is
fixed to `handshake_nested_hop_identity_once` version
`nested-hop-host-key-identity-handshake/1`, with the sole side effect
`network_identity_handshake`. Its authority delta explicitly denies stage,
submit, cancel, fetch and arbitrary command authority. PR3 `/1` remains the
base mutation closure, but cannot enter a new PR4B submit without the exact
`/2` overlay.

## Ordering and receipts

The only permitted order is Stage A first-hop attestation, Stage B nested
hash-only identity-source attestation, then the second-hop host-key/identity
handshake. Each operation has an active at-most-five-minute
window, single attempt, zero retry and mutation disabled. The authority entry
does not accept raw successor artifacts: it requires the owner-issued sealed
closure, verifies its canonical digest, and revalidates its active `/2`
authorization. It then binds the actual Stage A and Stage B request
nonce/time/version and their owner-validated receipts to authorization
operations 0 and 1 before binding the handshake request, observation and
receipt to operation 2.

The handshake receipt does not accept caller-provided receipt digests or a
caller verdict about fingerprint equality. The owner consumes the actual
Stage A and Stage B request/receipt artifacts, replays the PR2 owners, computes
their canonical receipt digests, and compares them constant-time with the
request and final receipt. A separate handshake observation carries the actual
second-hop fingerprint-evidence digest. The owner compares it constant-time
with the approved second-hop host-key evidence from the exact identity
binding; a merely SHA-shaped or self-rehashed digest is rejected. Only after
that replay may the owner generate or accept a
`classification=verified` receipt.

All owner functions are offline validators/builders. They import no network,
SSH, PBS, Gaussian, subprocess or command-construction surface. PR4A only
recognizes the successor and still stops at `transport_integration_required`;
full PR3 current-state replay, trusted consumption, Stage A/B execution and
handshake execution remain PR4B work. Actual receipt replay and comparison in
this patch are offline artifact validation only.

## Compatibility, migration and rollback

There is no automatic migration. A future new submission needs newly reviewed
`/2` profile, request and authorization artifacts. Historical `/1` artifacts remain
byte-for-byte replayable but gain no new authority. Rollback is a reviewed
revert of this additive owner, schemas, model recognition, tests and docs. It
does not delete artifacts, consumption/uncertain state or remote data.

Offline success is not live compatibility evidence. This patch must stop for
independent L3 review and does not authorize integration, PR4B resumption,
deployment, Skill synchronization, SSH, RTwin, PBS, Gaussian or live smoke.

## Schema/Python and module-origin compatibility

All four successor schemas are closed and every object has
`required=properties`. Profile capabilities are a non-empty unique array in
both Schema and Python; order is not authority. The fixed first/second logical
config refs remain distinct by construction and both digests remain in the
profile self-hash, but Python adds no cross-field digest-inequality condition
that standard JSON Schema cannot express. New request/authorization/profile
IDs use the PR2 owner limit of 64 characters; historical `/1` IDs and approver
principals retain the frozen PR3 128-character acceptance range.

The handshake observation Schema no longer accepts a caller-supplied
`observed_fingerprint_matches_approved` field. Its structural Schema remains
hash-only; the owner supplies the contextual equality check against the exact
approved identity binding. The sealed closure is intentionally not a portable
JSON authority artifact: it is an in-process owner capability whose canonical
bytes and digest cannot be substituted for raw caller-owned artifacts.

Repository and packaged layouts resolve different exact `runtime_config.py`
origins for the scientific owner graph. The PR3 loader holds its import lock,
saves any same-name cached modules, installs only the resolved exact graph,
verifies internal module identities, and restores the original cache objects.
Import order therefore cannot grant authority or create a false closure
failure, and no global cache clear is used.
